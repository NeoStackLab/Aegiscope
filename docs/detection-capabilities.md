# Detection Capability Matrix

**Status: Active Windows development and validation.** No production monitoring build is released. Current private Windows development builds include sampled process inventory, TCP connection metadata, UDP local bindings, optional elevated TCP byte counters, opt-in DNS query-name collection, protected-folder notifications and a default-off sensitive-file ETW pipeline. These are development capabilities, not a production monitoring guarantee; File ETW and elevated TCP byte counters have not been validated in live product monitoring.

| Capability | Current status | Boundary |
|---|---|---|
| Running process inventory, PID, parent PID, name and reported start time | PARTIAL | Private Windows development build samples with a user-mode process API every two seconds and caps the snapshot at 1,024 processes. A complete process audit trail is not claimed. |
| Process start/stop changes | PARTIAL | Inferred by comparing complete two-second snapshots. Short-lived processes can be missed; no real-time process-start source is currently integrated. Validated transitions are retained locally for up to 30 days and 100,000 rows. |
| Publisher, signature, hash, version and redacted command line | PARTIAL | The private development build reads local version resources, checks embedded Authenticode signatures without online revocation lookup, computes bounded local executable hashes and displays locally redacted command-line metadata when Windows permits access. Protected processes and inaccessible, oversized or changing files can remain unavailable. These are identity clues, not proof of loaded code or a malware verdict; broader Windows compatibility and trust cases need validation. |
| Sensitive file access attribution | PARTIAL | A default-off System IO ETW metadata pipeline is connected to settings, bounded local summaries and a Sensitive Data view. It does not read file contents and has not been validated with live ETW records; permissions, attribution, event loss and path coverage remain open. Windows audit events require suitable audit policy and object SACLs. |
| Protected-folder change and file-size metadata | PARTIAL | Private development builds can watch selected protected folders and inspect an eligible file's logical size and Windows-reported allocation size after a change notification. These are current metadata snapshots, not event-time values, bytes written or physical-media usage. The notification does not provide a writer PID. A cautious correlation may associate the logical-size snapshot with nearby same-path write evidence, but that association remains an inference. After increasing the per-notification path cap to 512, one Windows 10 Enterprise build 19045 Release burst creating 2,500 files accepted 7,501 paths, reported zero Agent-counted drops/rescans/watcher errors, and drained its bounded queue. Incomplete coverage was still visible during backlog. This one run does not prove that Windows or every filesystem always delivers every notification; broader validation remains open. |
| Git history mass access | PARTIAL | The private development build can classify and aggregate Git-history path metadata through the opt-in file pipeline. No live Windows ETW validation has been completed; it does not establish that file contents were consumed. |
| Large logical file-size setting | PARTIAL | The private development build can summarize a successful Windows file request that sets a logical end-of-file size of at least 1 MiB. The signal does not prove file creation, allocation, or that bytes were written; ETW fields and coverage have not been validated live. |
| Archive-like writes followed by outbound TCP activity | PARTIAL | The private development build can observe successful writes to archive-like filename suffixes and correlate them with later same-destination TCP activity. A suffix does not prove archive format, contents or compression, and TCP counters do not prove those contents were sent or received. The relevant file and elevated network sources remain unvalidated live. |
| Secret-value inspection | UNSUPPORTED | Intentionally excluded; intended model is metadata/path classification. |
| Current IPv4/IPv6 TCP endpoint metadata by PID | PARTIAL | Private Windows development build samples IP Helper owner-PID tables every two seconds, omits listeners and caps display at 2,048 rows. It is not a connection audit trail and can miss short-lived connections. Process name/path is joined by PID and can be incomplete or stale. |
| Current IPv4/IPv6 UDP local endpoint metadata by PID | PARTIAL | The private development build samples IP Helper owner-PID tables every two seconds and caps display at 2,048 rows. Windows can report PID 0 when ownership is unavailable. These are local bindings only, not remote peers or proof of datagram traffic; live visibility needs validation. |
| UDP remote peer and event-byte estimate by process | PARTIAL | The owner-PID table reports local bindings only. A separate opt-in user-ETW collector can observe process/socket tuples and directional event-byte estimates, with loss and attribution gaps disclosed. Controlled IPv4 and IPv6 loopback tests passed on one Windows 10 Enterprise build using a non-elevated Performance Log Users token. Remote-network coverage, other Windows builds and service scope remain unvalidated; event bytes are not proof of delivered payload. |
| Per-process TCP sent/received data-byte deltas | PARTIAL | Optional per-connection Windows TCP counters can be grouped to a process identity after sampling. Enabling them requires an elevated token; the current validation session was denied access. They can miss short-lived connections, include retransmitted sent data, and do not represent UDP/QUIC, lifetime totals, application payload or confirmed remote receipt. |
| TCP user-ETW event-byte estimates | PARTIAL | A separate default-off TCP ETW path reports connection-scoped send/receive event-byte estimates and source gaps. Controlled loopback traffic and a short-lived connection history case passed on one Windows 10 host; process-start keys are not directly verified against a process-start event. Estimates may include control or repeated transmissions and are not accurate payload totals. Non-loopback, sustained-load, Windows 11 and service coverage remain unvalidated. |
| DNS query and answer-IP collection | PARTIAL | An explicit opt-in can collect future DNS Client events only when the Windows event channel is already enabled. It parses a bounded set of IP literals from event results and keeps query names/addresses in memory for up to 60 seconds; it does not persist them. The current host's channel is disabled, so live event and answer parsing are unverified. |
| Possible DNS name for a sampled TCP endpoint | PARTIAL | The Network view may show a candidate name when its parsed answer IP exactly matches a TCP remote IP and the DNS event preceded the snapshot by up to 60 seconds. This is only a time-and-IP overlap hint, not a connection-start, socket or process join. Shared/CDN IPs may match unrelated names; live DNS delivery remains unverified. |
| DNS-to-process attribution | UNSUPPORTED | No caller PID or validated process-attributed DNS observation is available. The possible-name hint above does not identify the application or establish which query created a connection. Caches, proxies and application-owned encrypted DNS can also prevent a useful match. |
| Persistence state changes | PARTIAL | Optional local snapshots cover selected Run/RunOnce registry entries, Startup folders, queryable services and scheduled tasks. They report observed state changes, not a writer process or a complete audit trail; polling, access visibility and other Windows builds need more validation. |
| Camera/microphone access attribution | UNSUPPORTED | No general product event feed implemented for arbitrary desktop processes. |
| Clipboard or screen capture attribution | UNSUPPORTED | No reliable monitor implemented. |
| Sensitive-file, staging and outbound correlations | PARTIAL | Several conservative local rules correlate ordered sensitive reads or Git history access with endpoint/traffic observations; other rules cover archive-suffix writes and first-observed TCP/UDP peers. They require same-process/socket evidence where available and retain LOW confidence plus payload/delivery unknowns. The optional File ETW source is not validated live under the current token, and current file-size notifications do not identify a writer. These rules do not prove a connection began after a read, an upload, or payload contents. |
| Git history → local size/artifact evidence → endpoint → outbound traffic | PARTIAL | A development-only simulation runs a high-confidence synthetic benchmark. The private development build also has a production correlation path using Git-history access, either a successful logical-size setting or a protected-folder size snapshot with a cautious same-path write association, a newly observed TCP endpoint and optional per-connection sent-byte deltas. When available, the alert separately shows the filesystem-reported allocation-size snapshot. This path remains LOW confidence and its file/network sources have not been validated in live product monitoring. It does not prove the file was created by that application or that its contents were sent. |
| Local visual rule editor and saved correlation rules | PARTIAL | Users can build ordered rules over currently supported process, file and TCP observations and save them locally. Process start/stop changes are based on two-second snapshots; child context is limited to selected sampled shell/loader processes. A match requires the same process instance and ordered observations. Rules do not establish file contents, encrypted payload contents or a maliciousness verdict; available evidence inherits each source's limitations. |
| Development simulation scenarios | SUPPORTED | The private development build includes ten deterministic scenarios for normal browser/IDE activity, repository snapshot behavior, credential/browser/document access, archive-like writes, persistence changes, unknown-application TCP activity and first-observed UDP event-byte estimates. Simulations are explicitly labeled and never substitute for unavailable production telemetry; they validate rule/UI behavior, not Windows sensors. |
| Block network action | UNSUPPORTED | No enforcement component; UI must not show a working block action. |
| Exact contents of encrypted HTTPS payloads | UNSUPPORTED | Not visible from connection metadata; decryption is not planned. |

## Candidate mechanisms to validate

ETW is a documented framework for consuming provider-defined application and kernel events; fields and availability depend on provider, OS version, permissions and event schema. Windows Security file-access events may require audit policy and matching SACLs. WFP offers application-aware filtering at ALE layers, but this does not establish payload contents or a validated per-process byte counter.

Validate attribution, event loss, privilege needs, overhead and interaction with Windows Firewall/security products on supported Windows 10/11 builds before changing status.
